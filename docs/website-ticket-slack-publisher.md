# Website-ticket Slack publisher

`0025_website_ticket_slack_outbox` is the transactional source of truth, and `0026_ticket_slack_edge_worker` adds the after-insert `pg_net` wake-up and one-minute `pg_cron` recovery call. Follow-up migration `0027_ticket_slack_description` adds the ticket description to outbox snapshots and Slack root previews; apply it and redeploy the Edge Function to enable descriptions. `pg_net` issues the HTTP request **after commit**, so a rolled-back or evidence-suggestion create cannot be published. The Edge Function and the existing independent hourly Python publisher claim the *same* outbox with `FOR UPDATE SKIP LOCKED`, ordering and a committed `sending` state before Slack POST. Neither path re-POSTs an ambiguous or stale claim. This is near-immediate best-effort delivery, not a synchronous Slack guarantee; save succeeds even if scheduling the wake-up fails, and the minute/hourly workers provide recovery. Uncertain delivery reconciles by hidden Block Kit IDs, with support for previously posted visible markers, or requires operator review.

Migration `0025` installs an empty outbox and a cutover timestamp. There is **no ticket backfill**: tickets created before it, Slack-origin tickets and evidence-suggested tickets are not published, including their later updates. A new website `committee_dashboard` create and its subsequent changes post one root and thread replies to `C0BQPDP5T44`. Event IDs are carried in invisible Block Kit section `block_id` values for safe reconciliation; ticket/event IDs do not appear as visible text, and the publishers still recognize old text markers during cutover. Root-preview IDs use a distinct prefix so a successful root update cannot be mistaken for a delivered thread reply. Root previews include the website deep link, status, assignee names (never guessed Slack mentions), and description. Roots posted before migration `0027` show the description after the next website change; no historical Slack message is rewritten by the migration. Existing thread replies are not rewritten. The Edge and Python publishers share the block-ID format, root update behavior, channel and website origin. Slack's section-block `block_id` is used as an internal identifier, and conversation history returns message blocks ([section block reference](https://docs.slack.dev/reference/block-kit/blocks/section-block/); [history support](https://api.slack.com/changelog/2018-12-a-bric-a-brac-of-broadcasts-built-with-blocks)). The Edge RPCs (verify, claim, finish, defer) revoke `PUBLIC`, `anon` and `authenticated` execution, granting only `service_role`; the function additionally requires a 64-hex-character `X-EFDS-Worker-Token` matching Supabase Vault **before** claiming. Do not expose the service key or the token in a website client or logs.

## Activation prerequisites and order (operator-run; nothing deployed here)

1. Confirm the target is Supabase project `immldithmugfrpojetmm.supabase.co`, inspect the **live** Alembic revision and GitHub Actions workflow, and take a database backup. If the live DB is still at the previously documented `82afe16026f6`, apply its intervening revisions (`0023`, `0024`, and `0025`) in the approved Alembic chain before `0026` and `0027`; do not infer production state from this repository. Confirm the hourly Actions workflow runs `scripts/publish_website_tickets.py` with `DATABASE_URL` and `SLACK_BOT_TOKEN`. Check that `pg_net`, `pg_cron`, Supabase Vault and `pgcrypto` (`extensions.gen_random_bytes`) are enabled, that migrations run with privileges to create Vault secrets, call `net.http_post`, schedule cron and create `SECURITY DEFINER` functions, and that `service_role` is present. Review the static function URL in `0026` if using another project. Do not apply migrations to an unconfirmed target.
2. Confirm the Slack app is installed in `C0BQPDP5T44`, with `chat:write` and the channel's read-history scope (`channels:history` for public or `groups:history` for private), and can call `conversations.history` and `conversations.replies`. Provision `SLACK_BOT_TOKEN` as a **Supabase Edge Function secret** through the protected dashboard Secrets UI or a private CLI env file outside the repo (never paste token into shell arguments, SQL, GitHub logs or chat). Edge runtime also requires its built-in `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; optionally set `WEBSITE_URL` to a trusted HTTPS origin (default `https://www.imperial-efds.com`). The GitHub Actions token is separate; do not remove it.
3. Run the tests below, then deploy the function *first* with custom authentication enabled: `supabase functions deploy send-ticket-slack --project-ref immldithmugfrpojetmm --no-verify-jwt`. Disabling Supabase gateway JWT enforcement is essential because `pg_net` authenticates using the private Vault worker token, **not** an Authorization JWT; the handler still rejects requests without a valid worker token verified by its service-role-only RPC. Verify the deployed function revision/configuration. Do not invoke it with a website user key.
4. Apply `0026_ticket_slack_edge_worker` and then `0027_ticket_slack_description` through the normal approved Alembic rollout. `0026` generates a 32-byte random worker token in Vault under `efds_ticket_slack_worker` if missing, never embeds its value in migration SQL, installs restricted RPCs and the enqueue trigger, and schedules `efds-ticket-slack` every minute. `0027` replaces the event snapshot function to include descriptions and refreshes queued snapshots; already-posted roots pick up descriptions on their next website change. Confirm the database revision, trigger, cron job, Vault secret **name** (not value), function deployment and minute-job logs. Rollout is forward-only: its downgrade intentionally requires review.
5. In a non-production/staging environment first, create a genuinely new website ticket and a subsequent assignment/status change; check the exact outbox event state and root/thread Slack timestamps. Exercise rollback, an uncertain Slack response and concurrency with the Python worker; do not interpret an empty-queue green job as successful delivery. Then approve production cutover. During production activation monitor `ticket_slack_outbox` pending/sending/uncertain, Edge batch logs and cron failures. The migration's wake-up trigger swallows transport-scheduling errors so ticket saves are not rolled back; the minute job recovers pending work. If an outbox item remains `uncertain`, inspect its Slack block ID (or a legacy text marker) before any manual reset; never blindly turn it back into `pending`.

The hourly workflow still syncs Slack archives, does **not** import Slack-origin tickets or repost legacy reminders, and runs the independent Python publisher regardless of archive freshness. It remains a backup if Edge or cron is unavailable. The Python worker exits nonzero on deferred/uncertain work to surface problems in Actions.
